## 1. 项目概况

### 技术栈

| 类别 | 技术选型 |
|------|----------|
| 框架 | React 19 + TypeScript 6 |
| 构建 | Vite 8 + @vitejs/plugin-react |
| 样式 | TailwindCSS 4 + tw-animate-css |
| 桌面端 | Tauri 2 |
| 数据请求 | @tanstack/react-query |
| UI 组件 | @base-ui/react + shadcn (CVA) |
| 图可视化 | @xyflow/react + @dagrejs/dagre |
| i18n | i18next + react-i18next |
| Lint | ESLint 9 (flat config) + typescript-eslint |

### 当前阶段判断

项目已完成主要信息架构和核心交互骨架，进入“从能用到更稳、更顺手”的优化阶段。当前前端不是缺少基础能力，而是需要进一步校正以下三类问题：

- **语义与交互一致性**：已有设计系统和组件规范，但局部实现存在偏离
- **复杂页面的状态组织**：`Shell` 与 `SessionsPage` 已承载较多行为逻辑
- **图视图与长内容场景性能**：Graph 相关链路更值得优先关注

## 2. 做得好的地方

### 架构基础

- **分层仍然清晰**：`app`、`pages`、`components`、`lib` 的职责边界整体可辨识，项目没有陷入完全扁平化
- **API 类型契约完整**：`src/lib/api.ts` 集中定义 Tauri 命令输入输出，前端调用点具备较强类型约束
- **异步状态选型合理**：React Query 与本地状态职责划分自然，`useLocalStorage` 也契合桌面工具型应用的偏好记忆需求

### 体验方向

- **设计语言较统一**：整体配色、密度、信息层级和编辑器式气质已经形成一致风格
- **列表与详情信息密度较高**：符合桌面端效率工具定位，没有走过度留白的展示型路线
- **自动选中首项的策略合理**：在会话浏览场景下，这有助于减少空状态和多一步点击

### 工程基础

- **TypeScript 与 lint 基础到位**：说明项目具备持续迭代的工程底盘
- **脚本约定清楚**：开发、构建、预览、Tauri 相关命令完整，团队协作成本低
- **模块命名总体可读**：即使未完全抽象到 feature 级别，阅读路径仍较顺畅

## 3. 主要问题与优先级

这里不按“能想到什么就列什么”展开，而按**真实风险优先级**排序。

### P0: 交互语义存在硬伤

#### 3.1 嵌套按钮导致语义无效且增加交互风险
**相关文件**: `src/pages/sessions/session-row.tsx`

`SessionRow` 外层是整行可点击的 `button`，在 manage mode 下内部又嵌套了一个选择框 `button`。这属于无效交互结构，风险高于一般样式问题：

- 浏览器语义层面不合法
- 键盘导航和屏幕阅读器行为可能异常
- 点击冒泡与焦点逻辑更容易出现边界 bug

**建议**:

- 外层改为非 `button` 容器 + 内部使用统一交互元素
- 或将整行点击与勾选操作拆为并列交互区，避免交互元素互相包裹
- 这项应优先于 Graph 样式整理

#### 3.2 组件规范执行不一致
**相关文件**: `src/app/shell/index.tsx`, `src/pages/sessions/session-detail-pane.tsx`, `src/components/error-boundary.tsx`, `src/pages/sessions/session-graph.tsx`

项目已有统一按钮组件与 UI 规则，但当前仍广泛使用原生 `<button>`。这会带来：

- 视觉状态不一致
- hover/focus/disabled 态分散
- 无障碍与交互规范无法通过组件层统一收敛

**建议**:

- 先梳理“原生按钮可接受的例外场景”
- 其余统一迁移到 `Button` 或抽成轻量交互原子组件
- 评审文档里应把这项列为“规范落地问题”，而非继续给出过高的代码质量评分

### P1: `SessionsPage` 的复杂度正在累积

#### 3.3 问题不只是“文件太大”，而是状态与行为耦合
**相关文件**: `src/app/shell/index.tsx`

当前 `SessionsPage` 同时承载：

- 搜索与 debounce
- browse/search 两套查询切换
- 分组聚合与折叠状态
- 自动选中首项
- 键盘导航
- 批量选择/删除流程

这说明真正的问题不是 JSX 太长，而是“数据衍生逻辑”和“交互行为逻辑”混杂在组件里。直接按视觉区块拆组件，只会把复杂度平移。

**更准确的建议**:

- 先抽 `useGroupedSessions`
- 再抽 `useSessionSelection`
- 再抽 `useKeyboardNavigation`
- 组件层只保留布局与渲染

**不建议**:

- 先机械地拆成 `ShellLayout.tsx`、`SessionsList.tsx`、`SessionControls.tsx` 然后把状态 props 一路透传

### P1: Graph 相关链路比列表更像真实性能热点

#### 3.4 Graph 当前的性能风险高于列表虚拟滚动
**相关文件**: `src/pages/sessions/session-graph.tsx`, `src/pages/sessions/graph/build-tree.ts`

当前 Graph 链路是：

1. 拉取完整 transcript
2. 按 `main_path` 过滤
3. 在前端构建树
4. 初始化 React Flow
5. 再做 fitView 与节点交互

这条链路的初始化成本明显高于“200 条以内会话列表”的普通渲染，因此如果要定优先级，Graph 应排在虚拟滚动前面。

**建议**:

- 先做节点规模与初始化耗时的量化记录
- 视规模决定是否做 lazy mount、渐进加载或 worker 化
- 若 Graph 不是主路径功能，可延后初始化，只在切到图视图后再挂载

#### 3.5 Graph 样式硬编码确实存在，但不是当前最紧急问题
**相关文件**: `src/pages/sessions/graph/nodes.tsx`, `src/pages/sessions/session-graph.tsx`, `src/pages/sessions/graph/node-detail-panel.tsx`

这些文件中 inline style 较多，确实不利于统一维护。但这更偏向“样式组织问题”，不应压过语义与性能主问题。

**建议**:

- 将节点尺寸、颜色、面板皮肤提取为集中 token 或样式层
- 保留少量与图布局耦合较强的内联样式
- 目标不是“消灭所有 inline style”，而是把可复用视觉规则集中化

### P2: 文案和渲染实现上有可维护性隐患

#### 3.6 `dangerouslySetInnerHTML` 用于计数文案，不值得
**相关文件**: `src/app/shell/index.tsx`

当前在“全选提示”和“已选数量”文案中使用 `dangerouslySetInnerHTML`。对这类简单数字文案来说，这会：

- 增加 i18n 文案维护复杂度
- 模糊文案与结构的边界
- 引入本不需要的 HTML 注入面

**建议**:

- 尽量改为纯文本插值
- 如果必须强调数字，优先用拆分节点或专门的小组件承载样式

#### 3.7 少量魔法数字已经开始扩散
**相关文件**: `src/pages/sessions/session-row.tsx` 等

如 `title.length > 80`、图视图固定高度、若干字号与尺寸常量都已出现。单看不严重，但会在后续细节调整时增加修改成本。

**建议**:

- 先提取“有语义”的阈值，而不是一股脑建立 `constants.ts`
- 例如：标题截断长度、Graph 最小高度、列表页骨架数量

### P3: 测试与导出风格属于后续稳态建设

#### 3.8 当前“零测试覆盖”值得记录，但不应泛化成覆盖率 KPI

现阶段更适合补：

- 格式化与时间相关工具函数
- 分组/筛选/排序逻辑
- 容易回归的键盘导航行为

**建议**:

- 先写少量高价值测试
- 不建议一开始就设“覆盖率 ≥ 70%”这类目标，否则容易产出低价值测试

#### 3.9 导出风格统一可以做，但优先级较低

`default export` 与 `named export` 不统一会影响阅读体验，但它不是当前影响稳定性的关键点。

**建议**:

- 作为重构顺手项处理
- 不需要单独占据高优先级动作位
